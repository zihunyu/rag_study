# 分阶段开发与审核编排规则

## 任务职责

- 开发任务：只完成当前已批准阶段，运行验证并提交阶段完成包；未经审核不得进入下一 Gate。
- 当前审核任务：读取开发任务状态、审查变更、运行必要测试，批准、拒绝或要求修复。
- 并行开发任务：仅用于可以独立完成且文件写入范围不重叠的工作包；同目录或同接口的并行修改必须串行。

## 阶段完成包

开发任务每阶段结束必须提供：

1. 本阶段需求和 WBS/FR 对应关系；
2. 改动文件、数据库迁移和配置 revision；
3. 单元、契约、集成、E2E、安全或评测证据；
4. 未解决缺陷、风险、技术债和用户配置阻断项；
5. 对上一 Gate 退出条件的逐项结论；
6. 下一阶段可并行工作建议及文件所有权；
7. 明确写出 `STAGE_REVIEW_REQUESTED`，然后停止推进。

## 审核结论

- `APPROVED:<gate>`：允许进入下一个阶段；开发任务收到后方可继续。
- `CHANGES_REQUIRED:<gate>`：只允许修复审核问题，不得扩展范围。
- `BLOCKED_USER_INPUT:<gate>`：列出用户必须填写的具体字段路径；可继续不依赖该字段的工作。
- `REJECTED:<gate>`：方案需要重新设计或重基线。

## 并行开发

- 项目当前不是 Git 仓库，因此在 Git 初始化前不允许两个开发任务同时写共享工作区。
- Git 初始化后，独立工作包应使用不同 worktree/分支；每个任务在开始前声明文件所有权。
- API/Schema、迁移、权限和索引状态机属于高冲突区域，只允许一个任务写入。
- 前端页面、测试数据、文档或独立适配器可在契约冻结后并行。

## 自动推进边界

- 审核任务可以自动批准测试、质量、安全和 Gate 条件全部通过的阶段。
- 涉及数据出站、生产资源、真实费用、权限放宽、删除策略、法律保留或新外部供应商时，即使测试通过也必须等待用户配置或明确授权。
- 自动推进不扩大沙箱、账户、网络、生产环境或外部系统权限。

## 强制本地启动与存储约束

- 全项目禁止 Docker、Docker Compose、Testcontainers、容器镜像和容器部署脚本。
- 后端、Worker、迁移、配置检查和辅助工具必须可通过 `python xxx.py` 直接运行。
- 前端必须提供 `npm run dev`。
- 内容存储固定使用可配置的本地文件系统，默认 `./data/storage`；运行数据必须被版本控制忽略。
- 依赖服务只允许本机原生服务、现有原生服务或 Python 本地/嵌入式适配器。
- 审核发现 Docker/Compose 文件、命令或必需依赖时，当前 Gate 自动判定为 `CHANGES_REQUIRED`。

## 权威配置边界

- 实际配置只允许 `config/.env`，且必须被 Git 忽略；唯一模板是 `config/.env.example`。
- 进程环境变量优先于文件；所有字段必须经过类型和条件校验。
- 配置报告只允许输出变量名、类型、来源、配置状态和错误码，不得输出值。
- 中间件只保留 MySQL、Redis；任务固定使用 Python 本地 SQLite 持久队列。
- 检索部署只允许 Zilliz Cloud 中国区，通过 `pymilvus.MilvusClient` URI + Token 契约连接。
- 任何旧 YAML、旧用户配置目录或第二配置入口出现时，配置迁移审核不通过。
