# 问答预算与预算不足时的行为

本次只改当前项目后端，不连接 0727 的数据库，也不重新分块、重建索引或向量化已有资料。
预算默认启用；现有配置未填写新增字段时采用下面的默认值。

## 默认额度

| 模式 | 检索查询总数 | 首轮查询数 | 模型 HTTP 尝试数 | 输入 token | 输出 token | 整轮时限 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 简单事实 | 2 | 1 | 16 | 100,000 | 16,384 | 180 秒 |
| 普通 | 4 | 最多 2 | 24 | 200,000 | 32,768 | 300 秒 |
| 深入 | 8 | 最多 2 | 48 | 400,000 | 65,536 | 600 秒 |

这些是初始上限，不是每次必须用满的次数，也不是正确率或价格承诺。
额度按一次问答执行分配；手动重新提问或进程中断后的任务重放属于新执行，
不是跨重启的额度账本，也不是账户每日/月度费用上限。
`reading.budget_profile=auto` 在本地保守识别短小的单一事实问题，其余采用普通模式。
识别过程不调用模型。`standard` 强制普通模式；只有明确传入 `deep` 才启用深入模式。
现有 `reading.mode` 仍决定事实检索/逐章阅读方式，和预算档位分别设置；逐章阅读沿用原有
章节、块数及图片数限制，但它的模型调用也共享本轮预算。

检索上限分别由 `RETRIEVAL_MAX_SUBQUERIES` 和 `RETRIEVAL_DEEP_MAX_SUBQUERIES` 控制。
简单问题取普通上限与 2 的较小值。关闭 `RETRIEVAL_QUERY_PLANNING_ENABLED` 会把所有档位
限制为单查询。独立 `/api/search` 保持自身单次搜索规划上限；本方案的完整预算作用于问答入口。

模型预算的配置名称为 `QA_BUDGET_{SIMPLE|STANDARD|DEEP}_MAX_MODEL_CALLS`、
`MAX_INPUT_TOKENS`、`MAX_OUTPUT_TOKENS`、`TIMEOUT_SECONDS`，见 `config/.env.example`。
原有接口总时限、模型单次时限、核验阶段时限、账户限流仍然生效，取更严格者。
例如 `reading.mode=fact` 的接口外层仍受 `QA_FACT_TIMEOUT_SECONDS` 限制；若要完整使用深入模式
的 600 秒，需要相应调整该外层限制。文档内容与向量缓存不会因这些问答额度调整而重新生成。

## 检索额度分配

1. 原问题始终参与首轮；复杂问题首轮至多增加一个关注点，为补查保留额度。
2. 证据评估给出覆盖状态和缺失方面，每次只执行一个尚未查过的补查查询。
3. 新证据出现后再评估；覆盖充分立即停止。没有新来源，或新增来源未改善已选证据/缺口，提前停止。
4. 所有查询固定在同一租户、知识库、文档范围、发布版本及权限上下文中；缓存命中不返还查询次数。
5. 实际查询在最底层检索入口登记，失败尝试仍计数。单个查询可同时使用关键词和向量通道，
   所以“4 次查询”不等于“4 个 HTTP 请求”。

## 生成与核验预留

检索、上下文解析和证据选择最多占整轮模型调用数、输入/输出 token、时间的 50%。
为生成保留 15%，为核验保留 35%。生成阶段可使用尚未花掉的检索额度，但总使用量不能超过 65%；
独立核验阶段可使用剩余总额度。后续回答修复仍按生成阶段限制执行，并继续独立核验。
这是准入预留，不保证任意大小的生成或核验请求都能放入剩余额度；超大请求会明确停止。

HTTP 发送前原子预留，并发分支共享同一对象。每次重试都重新预留，预算不足不会被当作
供应商暂时故障自动重试。没有真正发送的请求会退回预留；已经发送但失败/缺失 usage 的请求
保留估算额度，不能按零费用处理。文档向量和问题向量命中缓存时，不发生模型 HTTP 扣次。

token 使用本地估计加安全余量做调用前检查，图像按独立预估额度处理；不是供应商精确计费分词器。
收到 usage 后使用供应商输入/输出 token 修正，实际值超过预留也完整计入，不截断到预算上限。
因此这是防止继续超支的准入控制，不是绝对账单封顶。未知 usage 会体现在 `unknown_usage_calls`。
本次没有新增人民币预算：不同模型的单价未必齐全，现有费用统计仍按已配置单价计算。

时间使用同一个单调时钟截止点，阶段、排队和重试不能重置它；模型网络超时会收紧至阶段剩余时间。
外层接口不会因为返回预算不足结果时截止点刚好耗尽，而覆盖已经保存的结果。

## 返回结果

| 情况 | 结果 |
| --- | --- |
| 有可独立回答的部分，且通过独立核验 | `answered`，`coverage=partial`，保留引用及未确认部分的状态 |
| 缺失关键前提，无法得出所问的整体结论 | 暂不生成整体结论，返回证据不足或预算不足 |
| 检索或模型预算不足，且没有可发布的核验答案 | `budget_exhausted`，不附答案/引用，`retryable=false` |
| 本轮可用证据不足，没有预算拦截 | `insufficient_evidence`；不表示已证明整个知识库没有答案 |
| 供应商故障、权限核对失败等 | 保留原有 `system_error` 路径 |

`coverage_report.retrieval_budget` 包含档位、上限、实际次数、剩余次数、首轮上限和停止原因。
`coverage_report.budget` 包含模型调用数、token 计数、未知 usage 数、总时限和预算拦截阶段。
`answer_scope` 区分已回答、部分回答、未回答。管理员报告还保留缺失方面和已引用证据编号；
普通读者只接收允许公开的运行统计，不能借报告读取未引用的内部来源信息。
回答预算不足时应缩小范围或明确选择深入档位；不会悄悄切换深入模式或重试完整问题。
这些字段及新状态已接入后端持久会话、普通问答和流式问答。本次没有增加前端档位按钮。

证据是否支持某个方面、是否缺少关键前提，仍由证据选择和独立核验共同判断；预算控制本身
不构成事实正确性的证明。需用真实知识库的固定测试题比较回答覆盖率、核验通过率、p95 等待时间、
每题实际 token 和停止原因比例，再调整档位。

## 接口使用

普通 `/api/ask`、`/api/ask:stream` 和会话消息的 `reading` 对象均支持新字段。例如：

```json
{
  "question": "比较两款设备的保修期限、费用和所需凭证",
  "space_id": "已有知识库 ID",
  "reading": {"mode": "auto", "budget_profile": "deep"}
}
```

省略 `budget_profile` 就自动选择简单或普通档位。请求不能自行传入更大的 token/调用数，
这些额度由服务器配置掌握；配置变更后需重启后端和 worker。
