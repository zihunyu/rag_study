## 完成内容

| 问题 | 现在的处理 |
| --- | --- |
| 已算好的结果被缓存故障挡住 | 向量缓存初始化、读写或锁文件发生存储故障时，仍返回已经校验通过的向量。写入失败的向量先留在有容量和期限限制的内存中；重试优先复用，并尝试重新保存。答案副本的缓存异常也不会挡住已核验答案。缓存保护不放过错误的模型响应、维度、数值或引用。 |
| 换个问法就漏掉一个要求 | 扩展中文逗号、英文逗号、并列问句，以及不以“请列出”开头的属性问题。保留引号里的名称和“同时满足 A 和 B”这样的共同条件；检索和核验始终保留完整原问题。 |
| 有证据但只提示漏答 | 核验发现 `answer_missing` 或有证据的 `partial` 后，最多补答一次，只提供对应的遗漏证据。原答案和已有事实保持不变，合并后重新进行完整核验。新增冲突会阻止放行；预算不足、补答失败或新内容未通过核验时，保留原来已核验的部分。尚有可补项的答案不会进入整份答案直接复用缓存。 |
| 总结时先读取无关文档 | 优先按用户指定文档或文档名确定范围；否则先做一次受权限约束的检索，再用相关性选择器挑出文档，之后才读取章节。无法定位时不遍历无关正文；明确要求全库总结时保留全库读取。结果记录实际选中的文档和范围确定方式。 |
| 一次检索重复读取模型身份 | 同一次检索中的入口检查和两个检索分支共享成功检查结果；并行分支也可复用。下一次检索重新检查，不跨请求缓存权限，也不把不同模型、配置、索引代次混用。 |
| 未改文件仍逐一读取正文和查询状态 | 同步工具使用文件身份、大小、修改时间和可靠的内容变更时间判断变化，结合周期性全文哈希复核。内容记录、文档版本状态和队列状态批量读取；仍检查租户、空间、最新版本、文档状态和实际处理完成状态。 |
| 缓存与统计长期累积 | 文档向量和问题向量采用不同保留策略；旧缓存按文档策略接管。完成的统计明细先合并累计用量，再清理明细；历史未知用量仍然标记未知。正在进行的任务不被清理。Worker 每 10 分钟尝试维护，各项维护故障相互隔离。 |

## 默认保留规则

所有新增配置均已加入 `config/.env.example`，已有 `config/.env` 不添加这些项目也会使用默认值。

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `EMBEDDING_CACHE_DOCUMENT_RETENTION_DAYS` | 365 | 文档向量副本闲置保留天数 |
| `EMBEDDING_CACHE_QUERY_RETENTION_DAYS` | 30 | 问题向量副本闲置保留天数 |
| `EMBEDDING_CACHE_DOCUMENT_MAX_MB` | 16384 | 文档向量缓存的内容容量目标 |
| `EMBEDDING_CACHE_QUERY_MAX_MB` | 512 | 问题向量缓存的内容容量目标 |
| `EMBEDDING_CACHE_MEMORY_MAX_MB` | 64 | 向量保存故障时的进程内重试缓冲容量 |
| `EMBEDDING_CACHE_MEMORY_TTL_SECONDS` | 600 | 内存重试缓冲保留时间 |
| `REUSE_RAW_RETENTION_DAYS` | 90 | 完成任务的统计明细保留天数 |
| `REUSE_SUMMARY_RETENTION_DAYS` | 730 | 汇总记录保留天数 |
| `REUSE_MAX_FINISHED_ATTEMPTS` | 100000 | 完成的明细尝试数量和汇总任务数量的容量目标 |
| `DIRECTORY_SYNC_CONTENT_RECHECK_HOURS` | 24 | 未变化文件仍需重新计算全文哈希的间隔 |

文档使用过的向量不会因为随后被问题查询复用而降为短期缓存。缓存容量按内容字节估算，不等同于 SQLite 文件大小；维护分批进行，临时超出目标后逐步回收，释放的数据库页面供后续复用。维护只处理副本和统计，不删除知识库原文、分块或 Milvus 索引。

目录同步的正常入口是 `scripts/sync_directory.py`。加上 `--verify-content` 可以强制所有文件重新计算内容哈希；此操作本身不调用 Embedding。只有配合 `--apply` 且检测到需要入库的变化时，才提交处理任务。Windows 本地 NTFS/ReFS 使用独立于修改时间的 ChangeTime；不支持可靠检测的文件系统回退为全文读取。
