# 问答耗时原因与保留核验要求的提速评测

## 范围和结论边界

本次分析实际慢问答的调用流水，并建立独立调度实验。没有替换线上模型、减少证据、缩短原文、关闭图片或冲突检查，也没有把实验并行器接入生产问答。

“检查项和输入完全不变”可以通过请求摘要和故障注入验证；“任意问题准确度绝对不下降”不能由少量模型实验保证。因此采用**不允许准确性退化**作为上线验收条件，而不把一次通过当成普遍保证。

结论：条件并行有明显速度收益，但本次还没有通过“无损”上线门槛。一组全部判定一致且核验快 55.1%；另一组出现条件适用性判定差异；繁忙额度窗口还出现超时。因此维持生产串行，优先解决判定稳定性和额度调度，再接入并行。

最慢一题的近似时间线：

1. 理解提问与上下文：7.1 秒。
2. 向量、排序：10.3 秒。
3. 四张图片复查及两次独立核对：54.5 秒；证据选择两次：11.6 秒。
4. 初次生成：21.9 秒。
5. 第一轮核验及协议纠正：约 101.8 秒。
6. 因条件漏项触发补全：40.2 秒。
7. 对补全答案重新执行完整核验：约 80.3 秒。
8. 其余本地处理、查询和持久化：约 4 秒。

三次成功运行的 HTTP 流水均为 200，没有观察到 429。原始慢请求中，模型调用累计时间与整轮时间相差仅约 3～9 秒；数据库和页面渲染不是主要耗时项。这里的模型调用耗时包含本地额度等待，旧流水不能独立拆出等待与上游服务时间。

### 代码中的具体原因

- `adapters/model_http.py::OpenAICompatibleClaimVerifier.verify` 逐批同步核验，六批等待时间相加。上一轮修复解决了容量失败，并没有使批次并行。
- `infrastructure/visual_evidence.py::VisualEvidenceSession.__call__` 按图片顺序执行复查；一张图的初审通过后，再等待独立核对。不同图片之间本可安排独立任务。
- `application/qa.py::_ask` 的条件补全后必须重新核验整份回答。最慢一题因此多付出了约 120 秒。减少误判导致的无效补全有潜力，但不能通过跳过二次核验实现。
- 搜索结果会带入父片段和未引用冲突上下文。最慢一题最终有 52 个证据片段、85 个条件候选；生成只使用少量来源，但核验必须处理完整证据池。整轮累计输入约 **450,105 token**，这是多次调用的输入总和，不是独立知识量。
- 现有 `RedisVerifiedAnswerCache` 缓存的是已经通过核验的答案草稿，命中点在检索和图片复查之后；命中后仍会执行模型核验。它不是“相同条件下直接返回已验证结果”的缓存。
- 章节读取已有缓存；图片的 `checked` 仅在单次问答 session 内复用，跨次提问没有同样的问答图片核验结果缓存。
- 对最慢输入做完全相同文本去重，只能省 424 / 66,612 个证据文本字符，低于 1%。简单删除重复文本不足以解决数分钟延迟。

## 对照实验方法

从已有成功运行读取原始证据包及 Redis 中的已核验草稿，冻结为私有输入。实验不重新生成答案，不写问答结果、不修改知识库。

实验代码：

- `backend/src/ragkb/evaluation/verifier_parallelism.py`：独立实验函数，没有生产入口。
- `scripts/evaluate_verifier_parallelism.py`：使用现有实际模型、HTTP 客户端、账户限流、30 秒单元/180 秒总体时限和有界重试；限制每个实验的真实调用预算。
- `backend/tests/test_verifier_parallelism_evaluation.py`：检查请求不变、条件顺序、缺失条件拦截、末批坏引用拦截、全池冲突拦截、并发和父请求上下文传递。

变化只有：基础事实与完整证据冲突检查通过后，将独立条件批次从串行改为最多三路并行，全部完成后按原顺序合并；不返回部分完成的核验结果。每批仍使用原模型、原提示词、原文、答案、条件编号、全局流程节点歧义校验和原重试规则。

比较时检查：初始请求完整 JSON 的 SHA-256 多重集合、输入 token、调用数、每项条件状态/来源/原文/答案依据、逐结论判定、冲突结果、引用与覆盖核验标志。解释文字的措辞不要求逐字相同。

### 已完成的实测

| 固定输入 | 串行核验 | 三路并行 | 耗时减少 | 结果 |
| --- | ---: | ---: | ---: | --- |
| 抗抑郁药问题：52 证据 / 85 条件，额度窗口空闲 | 82.832 秒 | 37.153 秒 | 55.1% | 两者通过；全部输入及核验判定、依据一致 |
| 同一输入，紧接上一轮执行，额度窗口繁忙 | 82.832 秒基线 | 69.031 秒后失败 | 不计作提速 | 部分批次额度排队后超时，不能发布答案 |
| 巴比妥类问题：41 证据 / 59 条件，两边额度窗口均空闲 | 57.835 秒 | 33.177 秒 | 42.6%，仅为运行时间 | 两者均拦截，但串行判缺 6 条、并行判缺 12 条；不满足判定一致要求 |

第一组成功对照：两边均为 7 次调用、172,848 个输入 token，没有用减少阅读量换速度；累计本地额度等待分别约 0.005 / 0.028 秒。
繁忙窗口对照保留为失败结果，不能只报告成功样本。单批观察到约 20.9 秒的额度等待；多个批次累计等待约 44 秒（并行累计值，不等于墙钟时间）。

第二组反转顺序先并行后串行，每次计时前等待 65 秒让本地滚动额度窗口消退；这段实验间隔不计入核验耗时。两边各 5 次调用、70,832 输入 token，初始请求摘要完全一致，全部 59 条都检查完；但 K11～K16 共 6 条的适用性结论不同。串行 1 条保留 / 52 条不适用 / 6 条缺失；并行 1 条保留 / 46 条不适用 / 12 条缺失。

差异出现在资料中的其他主题被当作本题必须说明的条件，甚至有“缺失”的解释同时说明该规则与问题无关。说明前次成功不代表模型回放判定稳定，这也会造成无效补全与整轮重做。请求一致不足以证明真实模型输出一致；目前不能把差异单独归因于并发，仍需串行对串行的 A/A 对照和条件归属专项修复。此样本不计为“准确度无损通过”。

本次共执行 31 次真实核验模型调用，包含繁忙窗口失败请求；没有新增整轮问答调用。7 项实验安全测试加 16 项既有分批核验测试，共 23 项通过；静态检查通过。这个测试数量不等同于 23 道真实知识问答。

另发现超时预算传递问题：`HttpxJsonTransport._account_post` 在进入账户额度等待之前接收 HTTP timeout，取得额度后未按剩余时间重新收紧传给 `DeadlineHttpClient` 的 timeout；实验中单批实耗 33.5 / 38.8 秒才失败，超过配置 30 秒。下一步应修正“排队消耗预算后仍给 HTTP 原时限”的行为，而不是拉长失败等待。

## 方案评估及建议顺序

| 方式 | 证据与检查是否改变 | 提速证据 | 结论 |
| --- | --- | --- | --- |
| 额度感知的 1～3 路条件并行 | 输入和检查保持不变 | 一组实测核验缩短 55.1%；另一组判定差异，繁忙窗口有失败样本 | 首选实验方向，先解决判定稳定性、控制额度、处理排队与失败取消 |
| 不同图片之间并行，单图初审→独立核对顺序不变 | 保留原计划图片、原图与双重核验 | 原运行图片阶段占 54.5～81.8 秒；尚未实际 A/B | 第二优先级，与条件批次共用账户预算，不盲目叠加并发 |
| 精确条件下复用已核验结果 | 同一问题、完整上下文和资料/权限状态下复用既有核验凭据 | 代码确认现有缓存省时范围有限；新缓存未实测 | 重复问题潜力最大，需要完整失效规则和最终授权复查 |
| 原文引用表、完全相同输入的中间结果复用 | 可以设计成可逆、可校验的复用 | 单纯相同证据文本去重不足 1%；当前逐结论来源已共享 | 辅助优化，不能宣称能单独解决分钟级等待 |
| 减少不相关条件误判造成的补全 | 涉及核验语义，需要评测 | 原运行补全及重新核验约 120 秒 | 应独立修正与验收，不能以提速为由放宽漏项拦截 |
| 减少检索数、跳过冲突/图片/条件、换更弱模型、降低检查强度 | 会改变证据或质量要求 | 没有符合本次要求的证明 | 不纳入“保留准确度”的默认提速方案 |
| 提前流出未核验草稿 | 改变答案发布条件 | 只减少看到文字的等待，不减少完整核验耗时 | 不作为准确答案提速 |

精确结果缓存必须绑定：问题及解析后的会话上下文、知识库和指定文件、阅读模式、索引发布代次、有效文档版本/内容、图片版本及审核结果、模型/提示词/规则版本、租户/用户/权限修订与资料有效时间。发布、撤销、权限或规则变更必须使缓存失效；返回前仍检查当前授权和引用有效性。不能按语义相似度直接复用。

## 上线门槛

1. 补充每次成功和失败请求的阶段耗时、模型调用数、输入输出 token、队列等待、缓存命中原因及运行编号；不需要持久化成功调用的原始提示词。
2. 先做同配置重复运行的 A/A 对照，量化模型本身的判定波动，再做串行/并行 A/B；分别评测额度空闲、连续请求、并发用户以及请求取消。
3. 使用现有 24 题、三个长资料问题及缺条件/错误引用/跨来源冲突/权限撤销/图片版本变化等回归。逐题比较必要事实、条件、来源、冲突和隔离；任何新增漏判或失败率升高都不开放默认模式。
4. 报告中位数与 P95、成功率、语义一致性和调用成本，不能只比较最快的一次。当前样本量不足以宣称整库普遍提速或准确度绝对不变。
