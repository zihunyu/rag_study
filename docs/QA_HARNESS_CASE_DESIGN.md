# Harness 案例与逐项验收设计

状态：2026-09-09 已完成四项实现。本文保留设计目标，实际能力、限额及操作以
[工作台说明](QA_ACCEPTANCE_WORKBENCH.md) 为准；验证证据见
[v2 交付记录](QA_HARNESS_V2_DELIVERY_20260909.md)。自动生成范围限定为用户选择的原文片段，
尚未提供整库章节覆盖率统计，不能把候选题数量当成全库覆盖率。

## 目标与使用者

管理员负责配置、预算、权限和故障定位；知识库负责人负责核对案例依据及验收结果。案例独立保存，知识库仍照常存放业务资料。系统的 `verified=true` 和运行完成都不是验收通过的充分条件。

先完善案例与逐项结果，再接入文档生成候选题和辅助语义评审。现有案例版本、运行恢复和比较能力继续使用。

## 主要表单

| 字段 | 用户操作 | 规则 |
| --- | --- | --- |
| 问题 | 输入问题，或从真实问答带入 | 必填；多轮问题可展开前置问答设置 |
| 预期行为 | 回答、部分回答、资料不足拒答、冲突拒答、澄清 | 部分回答要分别列出可回答部分和必须说明的未知部分 |
| 验收要点 | 每行一个可独立判断的事实、条件、未知项或禁止说法 | 允许同义表达；不得要求答案全文逐字一致；关键条件与对应事实保留关联 |
| 原文依据 | 选择文件及位置、保存原文摘录，再关联到一个或多个要点 | 使用已授权版本；一个要点可依赖多份文件；无资料案例记录已检查范围与预期拒答理由 |

案例编号由系统默认生成，可编辑；分类、读取范围、多轮历史及高级检查收在折叠设置中。必要引用要求随原文选择提供便捷配置，但不把每个背景依据都默认变成必要引用。

候选案例可先保存不完整信息。确认案例时检查问题、可判断的预期要求和依据是否齐全；需人工核对后才能用于正式验收。

## 可选检查模板

| 模板 | 负责人补充 | 程序和复核各检查什么 |
| --- | --- | --- |
| 普通事实 | 事实与限制 | 程序检查来源及回答状态；逐项检查实体、数值、条件和否定 |
| 清单完整性 | 经原文确认的各项内容；可选数量和编号要求 | 分别检查条目数、重复、连续编号及每项内容；数量达到不代表内容完整 |
| 跨文件综合 | 必要文件以及需要结合得出的要点 | 分开检查是否检索到、是否引用到、是否真正正确结合 |
| 条件与例外 | 适用对象、条件、例外和对应事实 | 不接受只出现关键词但归属对象错误的答案 |
| 资料不足 | 有依据部分、未知部分、禁止猜测的内容 | 正确保留可回答内容并说明未知；全无依据时允许正确拒答 |
| 冲突 | 相互冲突的来源及各自适用范围 | 必须发现真实冲突，不擅自选一份为准，也不能把不同适用范围误判为冲突 |

第一步优先实现普通事实和清单检查，其余沿用现有字段并逐步结构化。业务事实存入案例数据，检查器不写死药物、产品或具体答案。

## 逐项结果与整题结论

每个要点展示：预期要求、原文依据、实际回答片段、检查结果、说明，以及程序检查、模型建议或人工复核的来源。要点状态为覆盖、遗漏、错误、待复核；引用与格式另列，避免把格式问题等同于事实错误。

- 程序能证明的数量、编号、精确重复和引用范围问题，直接记录失败。语义重复、同义改写及条件归属不能仅靠字符串数量判断。
- 辅助语义评审必须对照事先确认的案例和资料，不能直接继承回答系统的核验结论；不确定时标为待复核。评审模型与程序也可能出错，需保留证据和复核记录。
- 关键要点有遗漏或错误，整题失败；未完成评审则待复核；超时或预算耗尽导致无法完成本题的，记为未完成。
- 通过要求全部必要检查及关键要点通过。负责人可以纠正模型建议并说明依据，保留修改历史；程序硬检查失败必须先修复或修正案例后重跑。
- 要点是否允许不适用在案例中预先明确，不能因为回答遗漏而事后自行排除。

## 十条清单案例示例

问题：某章节列出的使用原则是什么？预期：回答。依据：负责人确认的指定版本章节及十条原文。要点：分别保存原文十项，每项关联证据。检查模板：清单，十项，统一连续编号，不重复。

当旧答仅有前四项时：运行完成；前四项内容可有依据；内容覆盖 4/10；后六项遗漏；附加重复第四项另报重复与编号问题；整体验收失败。重复任意条目凑到十项也不通过。若答案使用不同措辞但完整保留十项含义、条件及引用，可以通过。

## 案例来源

1. 真实问题转候选题：带入问题、读取范围及实际运行定位，负责人填写预期要求。现有回答仅作问题现场参考。
2. 文档或章节生成候选题：选择授权资料范围及题数/预算，形成问题、预期要点和原文依据；每条依据可定位，负责人确认后进入正式案例。
3. 手动添加关键业务题：覆盖高频问题、边界条件、容易混淆的对象和资料冲突。

自动生成的要求必须基于所选资料，不能把某次检索结果当成全部原文，也不能把同一系统的当前回答当标准。生成题量不等于知识覆盖率；结果应显示已覆盖和未覆盖的章节范围。

## 版本、比较与权限

运行保存案例及要点版本、原文版本、读取与权限范围、被测配置和评审方式。要点修改保留稳定标识和历史；历史结果不随新案例覆盖。

同一组案例比较正确性、内容完整性、格式、耗时、调用量和用量。案例或资料变化时分组说明不可直接比较；评审规则变化需在同一规则下重新评估两侧，或标明不可直接归因于问答质量。正式回归绕过答案缓存；缓存命中性能应另列。

依据查看时重新核查权限，来源撤回或更新时提示需要重新确认，不向无权用户显示历史原文。案例预期不进入检索索引或被测问答请求，只供独立验收使用。

## 建议实现顺序与验收标准

1. 简化表单，建立要点与依据的关联，兼容现有案例；增加清单数量、编号和重复检查。
2. 结果页显示逐项证据与复核记录；用固定原文和旧答验证能稳定报告六项遗漏，并保留正确改写、正确拒答等正向用例。
3. 接入受预算控制的候选题生成与辅助语义评审；确认新步骤仍可暂停、恢复且记录调用。
4. 比较页增加逐项改善和退化，不把少回答、少跑题或评审口径变化当作提速收益。

每一步分别验证权限隔离、预期不泄漏给被测系统、快照不可被改写，以及程序失败不可被误标成验收通过。
