## 当前行为

- 小批量继续在一次核验中检查回答、引用、冲突及条件。
- 条件超过一批时，先核验原子事实、完整回答与引用，并对**完整证据池**进行一次冲突检查。
  证据池包含未引用来源；没有按条件批次拆开冲突来源，没有只检查答案选择的证据。
- 基础核验通过后，按原始顺序分批检查所有条件。条件编号、原文、来源及等价来源关系保持不变。
  每批携带完整问题、答案及对应原文上下文；条件是否与问题相关仍由核验模型判断；明确提示候选来自关键词检测，口诀中的“舍不得”等文字不自动构成禁止性条件。所有原文仍保留在事实和冲突核验中。
- 每批使用聚焦于条件的输出提示，要求通过答案段落编号提供覆盖依据；与小批量路径共用相同的适用性、原文引用、答案段落、否定限制和流程分支校验规则。
  全局流程节点上下文保留，不能因分批而把原本不唯一的节点误判为唯一。
- 任意一批缺少条件、协议不合格或超时，均不能发布部分核验的草稿。
  基础核验已经发现冲突时立即保留冲突结果，不用后续批次覆盖该结论。
- 对完全相同的逐结论证据使用共享引用，原子结论数量不变；图中允许使用的事实范围不同则使用不同引用。完整冲突证据仍全部保留。
- 每个核验单元最多一次协议纠正，共享该单元剩余时间。条件批次只重新检查不合格的条目，保留逐项校验成功的条目（含缺失条件结论）；数量不符时重查该批剩余待核验条目。结论编号数量或顺序错误同样进入有界纠正流程。
  所有 HTTP 调用仍经过原有调用计费、并发、限流和验收预算入口。

## 默认容量与时间预算

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| `VERIFIER_CONDITION_BATCH_SIZE` | 16 | 每批最多条件数 |
| `VERIFIER_CONDITION_BATCH_CHARACTERS` | 6000 | 每批条件原文字符上限 |
| `VERIFIER_MAX_CONDITION_BATCHES` | 16 | 最多批数，按条数最多 256 条；长条件可能先达到批数上限 |
| `VERIFIER_TIMEOUT_SECONDS` | 30 | 单个核验单元的总时间，含一次协议纠正 |
| `VERIFIER_TOTAL_TIMEOUT_SECONDS` | 180 | 完整核验的总时间，含所有批次；调用方较短的剩余预算仍优先 |

容量不足会在模型调用前明确失败；单条条件过长不会被截断，也不会只核对前若干条就放行。
大证据集会增加条件批次调用；完整冲突检查不在每批重复，调用数量与时间均有上限。
核验修订升级为 `conditions-v14-batched-full-conflict-review`，避免复用旧规则答案缓存。

## 失败定位

聊天页面按优先级区分：容量超限、条件补全资料超预算、核验超时、服务不可用、结论数量或编号错误、核验格式或引用校验错误。
容量提示不再被通用协议错误遮盖，超时提示不再被会话 `failed` 状态遮盖。

私有诊断新增 `verification_stage`、`batch_number`、`batch_count`、`completed_batches`、
`condition_count`；超时保留底层错误码。聊天技术详情与验收失败详情展示经过白名单筛选的阶段及批次元数据。
草稿、模型消息与自由文本诊断继续留在私有存储。适用性标志与“该规则超出问题范围”的解释明确矛盾时，要求模型纠正，不在本地直接改成通过。
