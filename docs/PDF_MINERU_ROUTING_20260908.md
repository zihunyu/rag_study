# PDF 的 MinerU 解析路由修复

2026-09-08。对象：`西药二润德速记口诀0607.pdf`，文档
`01a07f70-2cdf-746d-bc8f-da7fc67bc3a0`。

后续更新：2026-09-09 已将此规则推广到所有 MinerU 路由，详见
[统一解析策略](MINERU_LAYOUT_POLICY_20260909.md)。下文记录首次 PDF 修复时的范围。

## 原因与证据

- 原文件有 141 页，第一页存在可提取的文字层。原生产路由优先使用 `pypdf`，仅在整份
  PDF 没有可用文字时回退到 MinerU。因此这份 PDF 实际没有调用 MinerU。
- 数据库中该文档第 1–5 版的解析版本均为
  `pypdf-text:visual-document-v4:graph-facts-reviewed-regions`。
- 图片覆盖检查发现第 1、2、3、98、107 页存在矢量元素，将这五页渲染为整页 PNG。
  随后的图片补充处理删除了对应页面的正文节点，用图片识别结果替换。
- 当前第 5 版的六个图片资产分别为第 12 页的 `IM41.jpg` 和上述五张整页 PNG；
  与截图中的数量、`rendered/page-1.png` 位置一致。

## 修复后的行为

- 生产模式的文字 PDF 和扫描 PDF 都交给 MinerU，不再以存在文字层为由跳过。
- PDF 使用 MinerU 的版面解析结果及其插图、图表裁图；不先按矢量元素渲染整页，
  不再删除页面上的标题和正文。文本、公式附带的裁图不会交给图片模型。
- 保留 MinerU `text_level`，将有效的 1–6 级标题转为带层级的标题节点。
  `chart` 节点按图片占位替换，避免残留重复的旧图表描述。
- 显式配置的 PDF 解析器失败时保留原错误，不再由通用路由转交本地图片占位解析器。
- 本地离线模式、Office 图片处理和历史版本复核快照仍沿用各自的处理路径。

## 验证

- 140 项相关测试通过；最后的路由错误处理调整又通过 39 项定向回归。
- 变更文件 Ruff 检查通过，6 个生产源文件 MyPy 检查通过。
- 从原 PDF 抽取第 1、12 页，实际调用已配置的 MinerU API：约 9.45 秒返回 27 个节点，
  仅 1 张插图裁图，没有整页图片。
- 用同一真实返回 ZIP 本地重放标题转换，得到 3 个标题、23 段正文、1 张插图；
  此重放没有再次调用供应商。随后实际图片处理只处理该插图，其识别结果仍需人工复核。
- 实测结果、原始供应商结果及重放结果保存在忽略目录
  `artifacts/pdf-mineru-20260908/`。本次仅抽样验证，没有重跑全部 141 页。
- 确认任务队列为空且 Worker 空闲后，只重启已验证归属的 Worker；重启后心跳正常且空闲。

## 现有文档

现有第 5 版仍为原已发布版本，解析历史及人工复核记录没有改写。使用文档页面的
“重新识别为新版本”可按新链路重新解析，完成复核发布后新版本才参与问答。
